# HS1-44｜发布与 MCP 的交互规划

日期：2026-11-17。本文为方案输出，交由 HS1-43「发布与 MCP 的交互逻辑执行」实施；文中的新增工具和发布草稿均为拟议能力，目前尚未实现。

## 1. 目标与范围

让 AI 通过 MCP 理解版本目标、维护发布计划与范围、准备可核查的发布说明，把“整理版本”到“人工确认发布”连接起来。

这里的发布指 HeySO 的版本发布及交付快照。Git 提交、GitHub 合并、部署平台上线、域名和外部通知由对应执行工具处理，不能将 HeySO 标记发布等同于代码已经部署。

首期覆盖：版本上下文查询、创建/编辑未发布版本、工作项关联版本、生成并提交发布草稿、页面人工确认与回读结果。首期不提供 AI 绕过人工确认直接正式发布，也不自动验收工作项、不自动启动或结束 Sprint。

## 2. 现有能力与缺口

| 环节 | 当前能力 | 本方案补充 |
| --- | --- | --- |
| 项目查询 | query_project 返回 releases、工作项和项目 revision | 保留，新增精确版本上下文查询 |
| 工作项上下文 | get_story_context 返回目标项所属版本 | 保留，不用于取代完整版本范围 |
| 范围调整 | create_item / update_item 可设置 releaseId，支持 null 清空 | 复用现有业务校验，批量调整需有明确结果 |
| 网页版本管理 | 创建、编辑、归档/恢复、发布说明、人工发布、交付快照 | 复用原详情页面，增加 AI 发布草稿与审核区 |
| MCP 版本管理 | 当前工具清单没有专用版本创建、编辑、发布工具 | 新增下述拟议工具 |
| 交付验收 | submit_result 只交付目标工作项 | 不能拿工作项交付接口冒充版本发布 |

现有正式发布逻辑：版本不能已发布或已归档；必须有关联项且至少一个项处于配置认定的完成阶段；所有非终态项必须指定转入有效后续版本或退回待办；发布说明必填；发布时冻结完成项为 publishedStories、记录未完成项去向为 deferredStories。版本范围变化不应改变 sprintId。上述规则以共用领域逻辑为准，不能在 MCP 单独放宽。

“完成”按项目/类型工作流定义计算；只有配置了人工验收的流程才存在对应验收要求，不能把所有普通完成记录都宣称人工验收通过。已取消项单独汇总，不计入已完成交付快照。

## 3. 推荐交互流程

| 步骤 | AI / MCP | 用户界面与结果 |
| --- | --- | --- |
| 读取 | query_project 确认项目，再 get_release_context 读取版本 | 复用既有版本 ID，展示目标、日期、范围、状态统计 |
| 规划 | 创建/编辑未发布版本；明确指定工作项后关联 releaseId | 显示计划变化与范围变化，不顺带改负责人、验收标准或 Sprint |
| 准备 | prepare_release 返回草稿、完成项、未完成项、取消项和阻塞原因 | 用户能检查交付范围、证据、说明和延期去向 |
| 提交草稿 | submit_release_draft 保存说明、去向建议、核对依据 | 版本详情出现“待确认发布草稿”，版本仍未正式发布 |
| 人工确认 | 用户在原详情中编辑说明和去向并确认 | 服务端重新校验当前范围，原子完成发布与快照 |
| 回读 | get_release_context 读取最终结果 | 明确未发布 / 草稿待确认 / 已发布；已发布结果返回实际日期及冻结范围 |

若用户仅要求准备发布说明，AI 输出草稿后结束；不能把该请求解释为允许正式发布或部署。用户拒绝或要求修改时保留意见，AI 基于最新上下文修订草稿，不改为已发布。

## 4. 拟议 MCP 契约

沿用现有 fileId、projectId 定位方式。具体 schema 在实现时随本地和云端网关一起注册，不仅修改工具文案。

### 4.1 get_release_context（只读）

输入：fileId、projectId、releaseId。

返回：版本身份与计划字段、archived 标记、项目 revision、当前关联项与完成/进行中/待办/取消统计、非终态项、冻结交付快照、延期记录、发布说明、草稿及审核状态。已发布版本以冻结快照作为交付依据，不能用后续变更的实时项覆盖历史。

### 4.2 create_release / update_release（写计划）

输入：项目定位、expectedRevision、唯一 requestId、agent；创建填写 name，可选 goal/startDate/plannedDate；编辑提供 releaseId 和仅需修改的 patch。

规则：日期可留空，填写时需为有效日期且起止顺序正确；同一项目规范化后的名称唯一；已发布版本不允许改内容，归档版本先通过现有页面恢复。工具不接受 status=released，不允许绕过专用确认路径。

返回版本 ID、字段、当前状态和新 revision；重试复用同一 requestId。

### 4.3 prepare_release（只读预览）

输入：项目/版本定位，可选说明风格及明确的范围建议。

返回：当前 scopeHash、revision、按状态划分的范围、说明草稿、证据链接、需要处理的未完成项及可选后续版本、阻塞原因。scopeHash 覆盖版本计划、工作项身份和相关内容/状态/关联信息；算法与版本必须由服务端定义。

预览不修改工作项、不移动范围、不标记正式发布；缺少证据写“未提供”，不编造测试、部署或验收结果。

### 4.4 submit_release_draft（仅保存待确认草稿）

输入：项目/版本定位、expectedRevision、sourceScopeHash、requestId、agent、notes、dispositions（逐项映射至 backlog 或有效后续版本）、artifacts（用户可访问的证据链接）。

返回：draftId、draftVersion、draftStatus、版本当前状态和人工确认入口。

草稿至少记录来源范围、说明、建议去向、证据、提交人和时间。保存草稿不修改实际 releaseId，延期迁移只在人工正式确认时执行。范围不完整可保存为“需补齐”，但不能伪装成可发布；提交后需回读确认保存成功。

首期不新增可直接调用的 publish_release。后续若需要工具化正式发布，必须另行设计绑定版本、范围与草稿版本的一次性人工授权机制，不能用一般写权限或 AI 开关代替。

## 5. 页面与人工审核

保持现有版本详情、工作项和发布说明页签、发布/归档入口；增加草稿摘要及来源，不替换原详情为另一套页面。

确认前展示：版本目标和计划/实际日期；完成项与证据；未完成项逐项去向；取消项数量；待生效说明；与最新版本范围的差异。用户可修改说明及去向，拒绝或要求修改时记录意见。

正式确认时重新计算范围；若来源已变化，显示新增/移出/状态变化项，重新预览并要求用户再次确认。旧草稿不能覆盖他人编辑或悄悄发布新范围。

项目活动记录区分 AI 修改计划、AI 提交草稿、人工修改、正式发布及拒绝；不能把 AI 提交草稿记录成“人工验收通过”。

## 6. 正确性、权限与并发

- MCP 与网页共用版本领域逻辑和账号/空间权限。AI 是否获准执行工作项与是否可维护版本计划是两类权限，维护计划不自动授权任何工作项执行。
- 云端沿用现有读写授权机制，由网关核验读/写权限及项目归属；新增工具必须在网关注册和授权列表中同步接入。具体授权 scope 以实现时服务端实际支持为准，不能假定本地新工具自动在云端可用。
- 写计划和草稿使用 expectedRevision；遇到冲突重新读取、展示差异并重算，不进行无条件覆盖。scopeHash 用于绑定预览范围，不能取代权限校验。
- requestId 按账号/空间/动作去重；同 ID、同参数返回原结果，同 ID、不同参数拒绝。去重记录须可跨重启持久化，并与业务写入一致提交。
- 正式发布时将版本字段、完成项快照、延期去向、草稿状态及活动记录置于同一原子操作；任一校验失败不得留下部分迁移。发布确认本身也须可安全重试。
- 批量关联版本不能返回笼统“全部成功”。首期可复用 update_item 逐项返回成功/失败，并读取实际结果；若未来提供批量接口，再明确其原子性。
- 已发布快照保留，不通过重开版本来篡改历史；归档不删除范围、证据和历史。

## 7. 异常与恢复

| 情况 | 行为 |
| --- | --- |
| 无完成项 / 版本范围为空 | 返回阻塞原因，不正式发布 |
| 未完成项去向未填或目标已发布、归档、跨项目 | 明确到项，保留草稿并要求修正 |
| 登录过期 / 无权限 | 明确失败；不切换账号空间，不放宽校验 |
| revision 或 scopeHash 变化 | 返回冲突和差异，重新预览及确认 |
| 网络超时、结果不明 | 使用原 requestId 重试并回读，不生成重复版本或草稿 |
| 用户拒绝 | 保留意见与历史，版本维持未发布 |
| 证据无法访问 | 标注不可验证，不声称成果已验证或已上线 |

## 8. HS1-43 实施顺序

1. 提取并复用版本校验/发布事务，固定本地与云端一致的返回和错误结构。
2. 补充 get_release_context、版本计划写入，以及权限与持久去重。
3. 实现 prepare_release 的范围指纹、说明草稿和缺项提示。
4. 增加发布草稿存储、submit_release_draft、原详情内的审核区及失效提示。
5. 接入人工确认的原子发布、审计和重复确认保护。
6. 完成本地 MCP 与云端 MCP 各自的真实链路验证；同步工具目录、授权提示与帮助。

本规划不自动创建或重分配工作项；HS1-43 实施前确认本方案及云端服务能力。

## 9. HS1-44 规划成果验收标准

1. 说明现有能力、缺口、目标、首期范围和不在本次范围内的能力，区分 HeySO 版本发布与 Git/部署。
2. 给出查询、规划、预览、草稿提交、人工确认及回读的完整流程，标明 AI 与人的职责。
3. 定义拟议工具的输入、输出、写入影响和校验边界，并明确当前未实现的能力。
4. 定义完成项、未完成项、取消项、延期去向及历史快照的处理规则，保留工作流验收要求。
5. 给出权限、范围变化、并发冲突、请求去重、超时重试及原子发布的处理方式。
6. 描述原详情页的草稿审核与差异确认交互，保留现有版本详情能力。
7. 提供 HS1-43 的实施顺序与可执行的后续验证清单，规划内容经负责人确认。

## 10. HS1-43 后续实施建议验收清单

1. AI 可读取版本计划、完整范围、状态统计和历史冻结快照。
2. 创建/编辑未发布版本遵循名称、日期、权限与项目归属规则。
3. 关联/移除 releaseId 不改 sprintId；非法目标明确失败。
4. 草稿提交成功后页面可见，正式发布状态保持不变。
5. 用户明确确认后才正式发布；无完成项、缺去向或非法去向时阻断。
6. 预览后范围变化必定失效提示，不发布未经确认的新范围。
7. 只冻结完成项，保留未完成项去向和取消项信息，历史快照不随实时项变化。
8. 人工验收工作流不可通过发布动作绕过；普通完成流程按其实际配置判断。
9. 并发、超时重试、同请求重复提交和服务重启均不造成重复版本、重复发布或部分迁移。
10. 本地和云端分别提供 MCP→领域逻辑→存储→页面回读证据，未实现或未验证的环节明确标注。
